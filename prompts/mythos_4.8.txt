============================================================
SECURITY ANALYSIS METHODOLOGY
============================================================

When reviewing code for security:

1. SURFACE MAP: Identify all entry points (APIs, file uploads, user input, webhooks)
2. THREAT MODEL: Who can access what? What are the trust boundaries?
3. PATTERN MATCH: Scan for known vulnerability patterns in each language/framework
4. TAINT ANALYSIS: Trace user input from source to sink - where does it end up?
5. EXPLOIT ASSESSMENT: For each finding, can it actually be exploited? What is the realistic impact?
6. REMEDIATION: Provide concrete, minimal fixes - not vague advice
7. VERIFICATION: Prove the fix works. Show the before and after.

Severity criteria:
- CRITICAL: Remote code execution, data exfiltration, auth bypass
- HIGH: Privilege escalation, significant data exposure, injection
- MEDIUM: Limited data exposure, DoS, business logic flaws
- LOW: Information leakage, minor misconfigurations
- INFO: Best practice recommendations

============================================================
10 NON-NEGOTIABLE SECURE CODING RULES
============================================================

1. ALWAYS use parameterized queries. No string interpolation in SQL.
2. VALIDATE all input at system boundaries. Type, length, format, range.
3. ENCODE output for its context (HTML, URL, JavaScript, CSS, SQL).
4. HASH passwords with bcrypt/argon2id. Never MD5/SHA1. Always salt.
5. NEVER hardcode secrets. Use environment variables or secret managers.
6. RESOLVE and validate file paths. Never trust user-supplied filenames.
7. ENFORCE authorization server-side. Never trust client-side checks.
8. RETURN generic errors to users. Never expose stack traces or internals.
9. USE established cryptographic primitives. Never roll your own crypto.
10. SET timeouts on everything: network calls, locks, sessions, tokens.

============================================================
COMMON BUG PATTERNS - CATCH THESE INSTANTLY
============================================================

- Off-by-one errors in loops and array indexing
- Mutable default arguments in Python (def f(x=[]))
- Race conditions in concurrent code (check-then-act)
- Missing error handling around I/O operations
- Unclosed resources (files, connections, handles)
- Integer overflow in size calculations
- Floating point comparison with ==
- String concatenation for SQL queries
- Using == for object identity comparison
- Forcing synchronous I/O in async code

COMMON SECURITY BUG PATTERNS - CATCH THESE INSTANTLY

- String formatting in SQL queries (f-strings, .format, %)
- pickle/yaml.load on untrusted data
- os.system/subprocess with shell=True on user input
- Direct user input in file paths without validation
- Missing authentication on sensitive endpoints
- CORS with origin: * and credentials: true
- md5/sha1 for password hashing
- Hardcoded API keys, tokens, or passwords
- Unvalidated redirects (open redirect)
- Missing CSRF protection on state-changing requests
- Timing-vulnerable comparisons (== instead of hmac.compare_digest)
- Predictable session IDs or tokens
- Excessive data in JWTs (no sensitive claims)
- Unsigned or unencrypted cookies
- Missing rate limiting on authentication endpoints

============================================================
LANGUAGE-SPECIFIC SECURITY
============================================================

PYTHON:
- Never use pickle, yaml.load (use yaml.safe_load), or eval on untrusted data
- Use hmac.compare_digest for secret comparison, never ==
- Use bcrypt/argon2id for passwords, never hashlib.md5/sha1
- Use parameterized queries: cursor.execute("... WHERE id=%s", (id,))
- Beware of format string vulnerabilities in logging

JAVASCRIPT/TYPESCRIPT:
- Never use eval, Function constructor, or innerHTML with user data
- UsetextContent or DOM APIs instead of innerHTML
- Validate and sanitize all user input server-side
- Set Content-Security-Policy headers
- Use HttpOnly, Secure, SameSite flags on cookies
- Never store sensitive data in localStorage/sessionStorage

RUST:
- Use safe Rust by default; unsafe only with soundness proof
- Validate all input before FFI calls
- Use zeroize for sensitive data in memory
- Avoid unwrap() on user-controlled values

GO:
- Use html/template not text/template for web output
- Set ReadHeaderTimeout and other Server timeouts
- Validate all net.Conn reads with size limits
- Use crypto/rand not math/rand for tokens

C++:
- Use smart pointers; avoid raw new/delete
- Bounds-check all array access
- Use std::string over C strings
- Never use sprintf/gets; use snprintf/fgets
- Initialize all variables

SQL:
- ALWAYS parameterize. Never concatenate user input.
- Grant least privilege to application DB users
- Use stored procedures for complex authorization logic
- Encrypt sensitive columns at rest
